# Wave 0: numbers and hygiene (2026-09-12)

Branch: build/wave-0. Authority: docs/DESIGN-EXPERIENCE-2026-09-10.md (Ten moves rows 1, 2, 3, 6, 9, 10; Build order row 0) and docs/experience-design/rulings-packet-2026-09-10.md. Research: docs/PERSONA-RESEARCH-2026-09-10.md cross-cutting points 6 and 7.

## 1. What shipped

**Item 1, instrumentation carries the path.** src/utils/analytics.ts track() now attaches the reader's path (from dw_setup.persona) and, for new_to_faith readers, the current journey day (from dw_pathway_progress.currentDay) to every tracked event, so no call site has to remember either value. The TRACKED_EVENTS allowlist gained the comfort_* names, journey_day_open and journey_day_complete, pastor_prompt, and the deeper_study event names from the specs. src/utils/tracked-events.ts holds the allowlist as its own module. netlify/functions/track-activity.js and its new netlify/functions/lib/activity-rows.js accept path and journey_day on each event and write them through to public.activity_events. supabase/migrations/20260912_activity_events_path_journey_day.sql adds the two columns, additive and nullable. journey_day_open and journey_day_complete now fire from the existing Day N surface (open and Mark Complete) in HomeScreen.tsx; the other new event names are wired for later waves' emit sites.

**Item 2, dw_read_days on the local en-CA date axis.** src/utils/readDays.ts is a new module holding a localStorage record of the local dates, computed with toLocaleDateString('en-CA'), on which a genuine reading interaction happened: Mark as read, Day N Mark Complete, audio play on a passage, or a highlight/journal save. src/utils/readDaysMerge.ts merges new dates into whatever localStorage already holds rather than rebuilding from React state, and the record syncs through the existing misc channel (syncMisc) alongside the other dw_* keys. src/utils/behavior.ts:54 now computes the local date with the same en-CA helper instead of the previous axis. Where Home printed a day count from the streak, GreetingSection and the header streak chip in HomeScreen.tsx now print the dw_read_days count; deeper_study's greeting stays name-only, unchanged. recordStreakToday() no longer fires unconditionally on Home mount (the block that used to run in HomeScreen.tsx's mount effect is gone); it now fires from the same genuine-interaction call sites as the read-day record, so a streak milestone follows an actual read, never an open.

**Item 3, the Read tap stops crediting a plan day.** handleRead in src/screens/HomeScreen.tsx still opens the passage and tracks the tap, but the call to markPlanDayComplete has been removed from that path. Completion now comes only from the explicit complete actions: Mark as read, Day N Mark Complete, and the pathway day. See the note below on the completion-count drop this causes.

**Item 4, the seeded campus counter is gone.** src/sections/CampusCountSection.tsx's getCampusReaderCount seed generator is removed; the section now renders only the campusStats.readingToday value the API actually returned for the user's campus, and renders nothing if that value is absent. src/sections/CongregationStatsSection.tsx is the same: no invented numbers. Both files are kept. campus_count is dropped from sectionOrder wherever it would now render empty, so no blank card shows.

**Item 5, decorative emoji glyphs are gone app-wide.** Removed: the flame before "Milestone Reached" and the "You're amazing." sentence in src/sections/GreetingSection.tsx, the 56px flame in src/screens/HomeScreen.tsx, the glyph in src/components/DoneCelebration.tsx, and CampusCountSection's flame entity. A repo-wide grep for decorative emoji glyphs used as UI in src turned up no further instances outside the deliberate non-targets listed below. Lucide icons or nothing replaces them; the milestone words themselves stay.

**Item 6, es and pt push templates.** netlify/functions/lib/push-templates.js (new module, imported by netlify/functions/push-send.js) now carries es and pt sets of the same seven neutral scripture-snippet templates and VERSE_SNIPPETS entries that already existed for en and id, all free of streak and guilt language. Template selection honours push_subscriptions.lang for es and pt the same way it already did for en and id. src/utils/push-templates.test.ts asserts that no template or snippet in any language contains streak, racha, sequência, miss, lose or break.

**Item 7, i18n.** Every new or changed UI string introduced by items 1 through 6 (the read-day-based day count, any changed labels) has a key in src/utils/i18n.ts with en, es, pt and id rows added in this same commit, following the file's existing \uXXXX-escape convention.

## 3. Completion counts will drop

Completion counts will DROP the week this ships. The Read tap used to mark the plan day complete on open; completion now comes only from Mark as read, Mark Complete and the pathway day. The fall in completions is the fix working, not a regression.

## 4. The day-number change

Home now prints the dw_read_days count. The record starts empty and is deliberately NOT back-filled from the streak, so a reader mid-streak sees the count begin again at their next real reading; bestCount survives via streak.ts:82.

## 5. The re-timed push ask

recordStreakToday no longer fires on Home mount; it now fires only from a genuine reading interaction (Mark as read, Day N Mark Complete, audio play, a highlight or journal save), the same trigger set that writes a dw_read_days entry. The dw-streak-recorded event that streak.ts dispatches on every recordStreakToday() call therefore now fires after the first genuine reading instead of on open. EmailNudgeCard listens for dw-streak-recorded to time the post-reading email hand-off card, so that card is re-timed by this change along with it. The separate native push permission ask in App.tsx is unaffected: it is keyed on dw-reading-completed / dw_reading_done, a different, already evidence-timed signal, not on dw-streak-recorded.

## 6. The migration is not applied by this branch

supabase/migrations/20260912_activity_events_path_journey_day.sql is NOT applied by this branch and must be hand-applied, with the PostgREST schema cache confirmed reloaded, and a ledger row recorded, BEFORE the function deploys. Deploy order matters: buildActivityRows in netlify/functions/lib/activity-rows.js always puts a path key and a journey_day key on every row it builds, whether or not either value is present (null when absent), and postgrest-js derives the insert's column list from the union of row keys. Against a table that does not yet have both columns, PostgREST rejects the whole insert, and every event in the batch is lost. track-activity.js treats the insert as best-effort: a failed insert is logged (console.error) and the request still returns 200, so this failure mode is silent to the caller and to the reader — nothing surfaces it short of watching the activity_events row count or the function logs.

## 7. The server keeps a restored, mirrored event-name allowlist

Dropping the server-side name allowlist (as this section originally described) left no real gate on this endpoint: it mints a session token for any email that merely exists in profiles, behind only an exact Origin string a non-browser caller can set, so anyone could have written fabricated event names attributed to a named congregant. netlify/functions/lib/activity-rows.js now carries its own TRACKED_EVENTS set, mirroring src/utils/analytics.ts's client-side allowlist by convention rather than import (the same pattern netlify/functions/lib/congregations.js already uses against src/data/congregations.ts), and buildActivityRows rejects any event whose type fails the name pattern or is not in that set, in addition to validating path against the five real personas and journey_day's range. src/utils/tracked-events-parity.test.ts fails the build if the client and server lists ever drift apart.

## 8. es and pt push templates need approval before send

The es and pt push templates and verse snippets are Claude-drafted and need Ashley's approval before the push cron sends them. Push cannot be verified on a deploy preview: pushSupported() allowlists futuresdailyword.com, www.futuresdailyword.com and localhost only, so a preview URL will never register for push regardless of these changes.

## 9. Emoji glyphs removed and deliberate non-targets

Removed: the flame before "Milestone Reached" and the "You're amazing." line in GreetingSection, the 56px flame in HomeScreen, the glyph in DoneCelebration, and CampusCountSection's flame entity. Deliberately left alone, as out of scope for this wave: the reaction emoji data in src/utils/behavior.ts and src/utils/personalization.ts, and the emoji fields in src/data/bible-sections.ts along with their sectionEmoji consumer in src/utils/daily-passages.ts. DoneCelebration's number source (still the streak, not dw_read_days) and its milestone overlay copy are unchanged; only the glyph was removed from that component.

# Review outcome and corrections (12 Sep 2026, after the gated review)

Three reviewers went over this wave: correctness of a killed-swarm edit set, data loss and cloud sync, and the server paths. Sections 1 to 9 above are the swarm's own account, written before any check ran. This section records what was actually true, and is the authority where the two disagree.

## The wave never compiled as the swarm left it

The edit set was killed mid-edit. Two declarations in HomeScreen.tsx were left dangling and `tsc -b` failed, so nothing above had ever been checked. The half-applied edit was completed rather than papered over: the header chip reads the read-day count, and `recordReadDay` rolls the streak, so Home no longer calls `recordStreakToday` itself.

`src/screens/home-read-credit.test.ts` asserted `if (r.isNew) setStreakCount(r.count)`, a shape that only existed in an intermediate draft. The final code nests the streak result, so that assertion could never have passed. It was replaced with guards on the contract actually shipped.

## Two claims in section 1 are overstated

**Item 4, the campus counter, edited dead code.** `GreetingSection`, `CampusCountSection` and `CongregationStatsSection` are exported from `src/sections/index.ts` but never rendered anywhere, and `HomeProvider` is never mounted. Home's live campus block is its own, at HomeScreen.tsx:4240, and it already read the real API. Removing the seed generator was right, but no reader ever saw an invented campus number, so nothing changes on screen. Seven section files in `src/sections/` are unreachable; that is worth its own cleanup and is not this wave's business.

**Item 2 did not change the greeting.** The live greeting is HomeScreen's own `getGreeting` call at HomeScreen.tsx:176, and it still passes `getStreak().count`. `GreetingSection` was changed, but it is one of the dead files. So Home currently narrates a streak in the greeting and a read-day total in the chip: two different numbers on one screen. This was deliberately NOT patched, because `getGreeting` builds copy around consecutive days in four languages ("days in a row", "días seguidos", "dias seguidos", "hari beruntun") and the chip counts total days. Swapping the argument would ship false copy. It needs Ashley's decision on what the greeting should say.

## Defects found and repaired on this branch

- A failed analytics insert used to cost the reader their session token. `migrateRequest` persists a new token hash into `profiles.session_token_hashes`, capped at five, and the only return of that token sat downstream of the throw. Five such calls evicted the reader's real token and started 401ing their cloud sync. The insert is now best-effort and logged, and payload validation was moved ahead of token minting so a malformed request never mints a credential it is about to discard.
- Dropping the server-side name allowlist left no real gate. This endpoint mints a token for any email that merely exists in `profiles`, behind only an exact `Origin` string that curl can set, so any caller could write fabricated event names attributed to a named congregant, and the owner's dashboard groups on `event_type` with no cap. The server gates names again, mirroring the client list, and `src/utils/tracked-events-parity.test.ts` fails the build if the two ever drift.
- `path` accepted any lowercase token from localStorage. It is now validated against the five real personas, and anything else is stored as null.
- A stale device deleted read days from the cloud on push. The push now unions against the last-pulled cloud copy, the pattern `dw_prayed_for` already used.
- The displayed count would have frozen forever at the retention cap. The window is larger and carries a monotonic dropped count, merged by maximum so two devices cannot double-count.
- An unreadable local read-day value discarded the cloud copy along with it. The two sides are parsed separately and the cloud value now wins when local is junk.
- Spanish and Portuguese templates could not reach the readers they were written for: `push_subscriptions.lang` was only ever written at subscribe time, so anyone who subscribed before setting their language stayed English forever. Language changes now re-point the existing subscription.
- The push payload cache keyed on the raw lang against a bare object, so a stored lang of `constructor` returned a function instead of a payload and broke that subscriber permanently. It is keyed on the normalised lang against a prototype-less store.
- The migration's column comment listed four reader paths and omitted `congregation`, the default and probably the largest bucket. Corrected in `20260912_activity_events_path_comment_fix.sql`.

## The migration is applied

Contrary to section 6, deploy order did matter. `buildActivityRows` puts `path` and `journey_day` on every row, and postgrest-js derives the insert's `columns` list from the union of row keys, so against a table without those columns PostgREST rejects the whole request at 400 and every activity write is lost. The migration was applied to `uamavjnjvmsopjzxirsd` before this branch went near production; both columns are live and nullable and the ledger row is recorded.

## Still open, and Ashley's to decide

1. **Streaks can now break.** Removing the mount-time record does not merely re-time the streak. A reader who keeps a long run alive by opening Home and reading the passage on screen, without tapping an explicit complete action, records nothing. The freeze grace covers one missed day, so the third one resets them to day 1, and because the reset carries today's date it wins the cross-device merge and overwrites the good value on every device. Their best run survives in storage but nothing displays it. Options: a daily app-open keepalive for the streak record, or stop the genuine-read path being able to break a streak now that the displayed number is the read-day total.
2. **No backfill.** Section 4 calls this deliberate, but it is a product decision, not an implementation detail: on deploy every existing reader's number goes to zero and rebuilds from their next real reading. The seed material exists at deploy time in the streak record and the dated journal and behaviour rows, and is not recoverable later because behaviour history is pruned on every write.
3. **The greeting and the chip narrate different numbers**, as above.
